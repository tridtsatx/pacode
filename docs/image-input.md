# Картинки в промпте

Статус: реализовано (2026-10). Картинка доходит до модели по всем транспортам и
рисуется прямо в ленте диалога.

## Путь картинки

1. TUI: `ctrl+v` с картинкой в буфере, drag-and-drop файла (bracketed paste с одним
   путём к `png/jpg/webp/gif`) или `@путь/к/файлу.png` в автодополнении. Вместо пути
   в промпт вставляется чип `[Image 1 · 1.2 MB]` (обычный текст: двигается, переносится;
   backspace рядом с чипом удаляет его целиком). Картинка готовится сразу
   (`pacode_image::prepare`), ошибка видна тостом. Не больше 8 картинок на сообщение.
2. Протокол: `Request::UserMessage { text, attachments }`; `Attachment { mime, data
   (base64), name }`, поле необязательное (старые клиенты работают). В тексте чипы
   превращаются в `[Image K]`.
3. Демон (`pacode-core/src/attach.rs`): готовит ещё раз (готовые файлы не пережимаются),
   кладёт байты один раз в каталог `<data>/images/<sha256>.<ext>` и строит сообщение:
   `Text`, затем `ContentBlock::Image { mime, hash, source_path, width, height }`.
   В истории (SQLite) только метаданные. Старые записи читаются как раньше.
4. Транспорты грузят байты лениво по хэшу (`pacode-provider/src/vision.rs`).
5. Лента: `TranscriptKind::Images { images }` идёт сразу за сообщением пользователя или
   за вызовом инструмента; TUI читает те же файлы из общего каталога.

## Подготовка (`pacode-image/src/prepare.rs`)

Декодирование png/jpeg/webp/gif/bmp (у gif первый кадр), поворот по EXIF и удаление
метаданных перепаковкой, длинная сторона до 1568 px, PNG для скриншотов и графики
(и всего с прозрачностью), JPEG q85 для фото, потолок 5 МБ до base64, вход до 16 МБ и
12000 px по стороне. Оценка в токенах фиксированная: `w*h/750`, не больше 1600 (не длина
base64).

## Хранилище (`pacode-image/src/store.rs`)

Содержимое адресуется хэшем, файлы неизменяемы. Потолок 256 МБ и 2000 файлов,
вытеснение по LRU (mtime) один раз при старте демона, без таймера. Если файл вытеснен,
а история на него ссылается, в запрос уходит текстовая пометка `[image omitted: …]`.

## Транспорты

| Транспорт | Форма |
|---|---|
| `openai_compat` (OpenRouter, Gemini, Kimi, Z.AI, OpenCode, OpenAI, Ollama…) | `content` массивом: `{"type":"text"}` и `{"type":"image_url","image_url":{"url":"data:<mime>;base64,…"}}` |
| `codex` (Responses) | `input_image` с `image_url` = data URL |
| `devin` | в сообщении вложенное поле `10 { 1 base64, 2 mime }` и в тексте плейсхолдер `[Image N: путь]` |

Картинки из результатов инструментов (`read` на файле-картинке): ни chat completions, ни
Responses, ни Devin не умеют класть картинку в tool-сообщение, поэтому после всей серии
tool-сообщений добавляется одно user-сообщение «Images returned by the tool call(s)
above:» с картинками (не между tool-сообщениями: каждый `tool_call_id` должен быть
отвечен подряд).

### Vision

`ModelInfo.vision`. Источник: каталог провайдера (OpenRouter
`architecture.input_modalities` содержит `image`), иначе эвристика по id модели
(`vision::heuristic_vision`: gpt-4o/4.1/5, o-серия без mini, gemini, claude, kimi-k2.5+,
moonshot-v1-vision, GLM-*V, `-vl`, llava…); неизвестная модель считается текстовой.
Без vision демон отвечает до отправки: `model <id> does not accept images`; транспорт
дублирует проверку, а картинки из старой истории (после смены модели) заменяет
пометкой, чтобы история не «ломалась». Ручного переопределения в конфиге пока нет.

## Показ в ленте (`pacode-tui/src/ui/images.rs`)

Только клеточный рендер полублоками `▀` (верхний пиксель — fg, нижний — bg): ведёт себя
как обычный стилизованный текст — скроллится, обрезается и перерисовывается без
«призраков». Не больше 14 строк высотой и по ширине ячейки, пропорции сохраняются.
Сырые kitty/iTerm2/sixel-эскейпы в прокручиваемой ленте не используются; Unicode
placeholders kitty не реализованы (везде полублоки). `[ui] images = "off"` — одна
строка `[image: имя 800×600]`. Кэш декодированных клеток: 32 записи / 4 МБ, ключ
`(hash, cols, rows)`, владелец — `Transcript`, сбрасывается при ресайзе, `/clear` и
снимке; цвета не зависят от темы.
