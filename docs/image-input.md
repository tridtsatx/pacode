# Картинки в промпте — что нужно, чтобы это заработало

Статус: не реализовано. Заметка написана 2026-09-11, когда протокол Devin разбирался по живому
трафику и выяснилось, что картинки он принимает, а pacode их отправить не может.

## Где сейчас обрыв

TUI уже умеет половину дела:

- `crates/pacode-tui/src/clipboard_read.rs` читает PNG из буфера обмена
  (`wl-paste` / `xclip` / `pngpaste`) и возвращает `ClipboardImageResult::Image(Vec<u8>)`.
- `crates/pacode-tui/src/paste.rs:270` кладёт эти байты во временный файл через
  `state.pasted_images.create_image_file`, файлы чистятся в `cleanup_pasted_images`.
- `crates/pacode-image/` умеет рисовать картинку в терминале (kitty, iTerm2, halfblocks).

Дальше путь обрывается: в промпт уходит только путь к файлу текстом. В
`pacode_types::ContentBlock` (`crates/pacode-types/src/message.rs:22`) есть `Text`,
`Reasoning`, `ToolUse`, `ToolResult` — и ничего для изображения, поэтому ни один транспорт
картинку отправить не может.

## Что добавить

### 1. Тип

```rust
// crates/pacode-types/src/message.rs
ContentBlock::Image {
    /// base64 без префикса data:
    data: String,
    /// image/png, image/jpeg, image/webp, image/gif
    mime: String,
}
```

`ContentBlock` сериализуется в историю сессии (SQLite), поэтому мигрировать формат не надо —
это новый вариант тега, старые записи читаются как раньше. Учесть в подсчёте размера
(`ContentBlock::…  => text.chars().count()` рядом, строка ~157): для картинки логично
считать не длину base64, а фиксированную оценку в токенах, иначе одна картинка «съест» окно
в отчётах.

Каждый `match` по `ContentBlock` в воркспейсе должен остаться исчерпывающим — правило репо
запрещает `_ =>` для своих enum, так что компилятор сам покажет все места.

### 2. Транспорты

| Транспорт | Форма |
|---|---|
| `anthropic` | блок `{"type":"image","source":{"type":"base64","media_type":…,"data":…}}` в `content` сообщения |
| `codex` (Responses) | элемент `input_image` c `image_url` вида `data:<mime>;base64,<data>` |
| `openai_compat` | `content` массивом: `{"type":"image_url","image_url":{"url":"data:…"}}` |
| `devin` | сообщение (поле 3) получает вложенное поле `10 { 1 base64_data, 2 mime_type }`, а в тексте остаётся плейсхолдер `[Image 1: /tmp/devin-pasted-images/<…>.png]` |

Форма Devin снята с живого трафика официального CLI 3000.10.21, наблюдался `image/png`.
Остальные три — по документации провайдеров, перед реализацией проверить актуальность.

Не каждая модель принимает картинки. Нужен флаг в `ModelInfo` (`vision: bool`) и понятная
ошибка «эта модель не принимает изображения» до отправки, а не 400 от провайдера.

### 3. Ограничения по размеру

Правило репо: всё, что попадает в контекст модели, ограничено по размеру. Для картинок:

- кап на файл (ориентир — 5 МБ до base64) и на количество в одном сообщении;
- ужать до разумной стороны (~1568 px по длинной стороне — предел, с которого Anthropic
  всё равно масштабирует) перед кодированием;
- base64 раздувает на треть — считать лимит уже после кодирования;
- в истории хранить путь + хэш, а не второй экземпляр байтов, если картинка уже на диске.

### 4. TUI

- `paste.rs` вместо вставки пути кладёт вложение в состояние промпта и показывает чип
  `[Image 1]`, который можно удалить до отправки;
- превью через уже готовый `pacode-image`;
- `@`-автодополнение файлов: если выбран `.png`/`.jpg`, прикреплять как картинку, а не как текст.

### 5. Протокол клиент↔демон

`Request::UserMessage { text }` несёт только строку — понадобится вариант с вложениями
(`attachments: Vec<Attachment>`), иначе TUI не сможет передать байты демону. Это
единственное место, где меняется проволочный протокол.

## Порядок работ

1. `ContentBlock::Image` + учёт размера + исчерпывающие `match`.
2. Протокол: вложения в `UserMessage`.
3. Транспорты: `anthropic` и `openai_compat` первыми (ими покрыто большинство моделей),
   потом `devin` и `codex`.
4. TUI: чипы вложений, превью, `@`-файлы.
5. Флаг `vision` в каталоге моделей и ранняя ошибка.
